# Архитектура маркетплейса драгоценных камней

## 1. Цель проекта

Проект представляет собой учебный маркетплейс драгоценных камней. Пользователь может зарегистрироваться, пройти двухфакторную аутентификацию, просматривать каталог, фильтровать и сортировать камни, оформить заказ и общаться с другими пользователями в realtime-чате.

Продавец может создавать и редактировать собственные объявления. Оплата заказа имитируется отдельным сервисом.

Проект предназначен для практики микросервисной архитектуры, проектирования баз данных, авторизации, WebSocket-соединений, работы с Kafka, S3-хранилищем и планировщиком задач.

## 2. Архитектурный подход

Используется микросервисная архитектура в одном monorepo.

Каждый микросервис:

- имеет собственную зону ответственности;
- владеет собственными данными;
- имеет отдельную базу данных;
- не обращается напрямую к таблицам другого сервиса;
- взаимодействует с другими сервисами через HTTP API или Kafka-события;
- может развиваться и запускаться независимо от других сервисов.

Внутри каждого сервиса применяется Clean Architecture с разделением на доменную логику, use cases, интерфейсы и инфраструктурные реализации.

## 3. Микросервисы

### 3.1. `auth_service`

Отвечает за:

- регистрацию пользователей;
- вход в систему;
- хеширование и проверку паролей;
- выдачу access и refresh JWT-токенов;
- обновление и отзыв refresh-токенов;
- роли пользователей;
- отправку и проверку одноразовых кодов 2FA по email.

Основные данные:

- пользователи;
- роли;
- refresh-сессии;
- настройки 2FA;
- одноразовые коды подтверждения.

Другие сервисы не хранят пароль пользователя и не изменяют данные `auth_service` напрямую.

### 3.2. `catalog_service`

Отвечает за каталог драгоценных камней и объявления продавцов.

Возможности:

- создание объявления продавцом;
- редактирование и удаление собственного объявления;
- просмотр списка объявлений;
- просмотр отдельного объявления;
- фильтрация по виду камня, размеру, весу в каратах и стране происхождения;
- сортировка по указанным характеристикам;
- загрузка и удаление фотографий через S3-совместимое хранилище.

Основные данные:

- драгоценные камни;
- виды камней;
- характеристики камней;
- объявления;
- фотографии;
- статусы доступности.

Идентификатор продавца хранится как внешний идентификатор. Данные пользователя из `auth_service` в базу каталога не копируются без необходимости.

### 3.3. `order_service`

Отвечает за корзину и заказы.

Возможности:

- создание заказа;
- добавление товаров в заказ;
- просмотр собственных заказов покупателем;
- просмотр заказов продавцом, относящихся к его товарам;
- изменение статуса заказа;
- отмена заказа в допустимом статусе;
- взаимодействие с `payment_service`.

Основные данные:

- заказы;
- позиции заказов;
- история статусов;
- снимок цены и названия товара на момент заказа.

В заказе сохраняются цена и основные данные товара на момент покупки. Это нужно, чтобы изменение объявления в каталоге не изменяло историю уже созданного заказа.

### 3.4. `payment_service`

Отвечает за имитацию оплаты.

Возможности:

- создание платёжной операции;
- имитация успешной или неуспешной оплаты;
- хранение статуса платежа;
- публикация результата оплаты в Kafka.

Сервис не подключается к реальному банку или платёжному провайдеру. Его интерфейс проектируется так, чтобы в будущем платёжный провайдер можно было заменить отдельной инфраструктурной реализацией.

### 3.5. `chat_service`

Отвечает за realtime-чаты.

Возможности:

- создание диалога между пользователями;
- отправка сообщений через WebSocket;
- получение новых сообщений в реальном времени;
- получение истории сообщений через HTTP API;
- проверка доступа пользователя к диалогу.

Основные данные:

- диалоги;
- участники диалогов;
- сообщения;
- время отправки и статус прочтения.

На первом этапе сообщения хранятся в базе `chat_service`. Kafka может использоваться для событий уведомлений, но не заменяет постоянное хранилище сообщений.

### 3.6. `notification_service`

Отвечает за отправку уведомлений.

Возможности:

- отправка email-кодов 2FA;
- отправка уведомлений о создании и изменении заказа;
- отправка уведомлений об оплате;
- обработка событий из Kafka.

Во время локальной разработки письма отправляются в Mailpit. В будущем можно подключить внешний email-провайдер.

### 3.7. `scheduler-service`

Отвечает за периодические задачи.

Используется APScheduler.

Планируемые задачи:

- удаление или деактивация просроченных кодов 2FA;
- отмена неоплаченных заказов после заданного времени;
- очистка устаревших данных;
- публикация периодических событий в Kafka.

Планировщик не заменяет Kafka и не используется для обычного обмена событиями между сервисами.

## 4. Пользовательские роли

### `buyer`

- просматривает каталог;
- использует фильтры и сортировку;
- оформляет заказы;
- просматривает собственные заказы;
- участвует в чатах.

### `seller`

- просматривает каталог;
- создаёт объявления;
- редактирует и удаляет собственные объявления;
- просматривает заказы, содержащие его товары;
- участвует в чатах.

### `admin`

- просматривает пользователей;
- управляет ролями и блокировками;
- имеет доступ к административным операциям;
- просматривает системную информацию.

На первом этапе отдельная модерация объявлений не реализуется.

## 5. Взаимодействие сервисов

Синхронное взаимодействие выполняется через HTTP API. Асинхронные действия и уведомления передаются через Kafka.

Пример создания заказа:

```text
buyer
  -> order-service: создать заказ
  -> payment-service: создать платёжную операцию
  -> Kafka: payment.requested
  -> payment-service: обработать имитацию оплаты
  -> Kafka: payment.completed или payment.failed
  -> order-service: изменить статус заказа
  -> notification-service: отправить уведомление
```

Примеры событий Kafka:

- `user.registered.v1`;
- `user.2fa_code_requested.v1`;
- `order.created.v1`;
- `payment.requested.v1`;
- `payment.completed.v1`;
- `payment.failed.v1`;
- `order.status_changed.v1`;
- `chat.message_created.v1`.

События должны содержать идентификатор события, тип события, версию, время создания и полезную нагрузку. Изменение формата события выполняется через новую версию, а не незаметным изменением старого формата.

## 6. Хранение данных

Используется PostgreSQL.

В локальной среде допускается один PostgreSQL-контейнер с отдельными базами данных для сервисов. Логическое владение данными при этом сохраняется: сервис работает только со своей базой.

Предварительное распределение баз:

- `auth_db`;
- `catalog_db`;
- `order_db`;
- `payment_db`;
- `chat_db`;
- `notification_db`;

Для каждого сервиса миграции схемы выполняются через Alembic.

## 7. Файловое хранилище

Для изображений используется S3-совместимое хранилище.

В Docker Compose локально запускается MinIO. В базах данных хранятся ключи объектов и метаданные, а не сами изображения.

Бизнес-логика не должна зависеть от конкретного поставщика хранилища. Работа с S3 выполняется через отдельный интерфейс и инфраструктурную реализацию.

## 8. Авторизация и безопасность

Используется JWT-аутентификация:

- короткоживущий access token;
- refresh token с ограниченным сроком действия;
- хранение и отзыв refresh-сессий;
- проверка роли и владельца ресурса на защищённых endpoint’ах;
- хеширование паролей современным алгоритмом;
- ограничение частоты запросов на вход и проверку 2FA-кодов;
- одноразовые коды 2FA с коротким сроком действия.

Сервисы проверяют подпись и claims JWT, но не получают доступ к базе `auth_service` для каждого запроса.

## 9. Инфраструктура

Планируемые компоненты Docker Compose:

- микросервисы приложения;
- PostgreSQL;
- Kafka;
- MinIO;
- Mailpit;
- при необходимости Redis для кэширования или технических задач.

На начальном этапе Redis не является обязательным компонентом. Он будет добавлен только при появлении конкретной задачи.

## 11. Осознанные упрощения

- реальная оплата не подключается;
- модерация объявлений не реализуется;
- email отправляется в локальный Mailpit;
- SMS-провайдер не используется;
- один PostgreSQL-контейнер может обслуживать несколько отдельных баз в локальной среде;
- Kafka запускается в конфигурации, достаточной для локальной разработки;
- API Gateway и service discovery не добавляются до появления реальной необходимости.

## 12. Что не входит в первый этап

- полноценный frontend;
- реальная платёжная интеграция;
- доставка и расчёт стоимости доставки;
- отзывы и рейтинги;
- сложная модерация;
- Kubernetes;
- горизонтальное масштабирование production-уровня.
